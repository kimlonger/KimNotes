# v1.4.14：贴图显示与便签交互修复

## 问题与处理

1. 贴图跨越不同 DPI 的屏幕后，WinForms 会额外缩放子控件，导致实际图片画布大小偏离显式缩放比例。贴图现采用物理像素画布：只由原始图片尺寸和用户缩放比例决定宽高；取消系统建议的 DPI 尺寸变化，工具栏仍按所在屏幕的 DPI 布局。
2. 窗口缩放时保留的旧像素、子窗口尺寸失配和延迟的 WM_PAINT 会造成多层画面残影。缩放过程增加防重入保护，统一父、子窗口尺寸，并同步重绘完整窗口及子控件。父背景与图片使用同一绘图规则。
3. 100% 显示使用明确的原图像素源、目标矩形，避免图片 DPI 元数据或插值使 1:1 显示失真。缩放仅影响显示，不更换、重采样或压缩原图。
4. 新便签默认宽度改为工具栏按钮、固定间距、左右内边距及窗口边缘的总宽，不再用 336 的舒适宽度留下额外空白。按钮大小、顺序和用户已保存的布局继续保留。
5. 便签启用网址识别，点击 HTTP/HTTPS 网址通过系统默认浏览器打开，www 地址补为 HTTPS。普通文字及非网站 URI 不交给系统启动器。测试使用替身启动器，不打开真实网站。
6. 便签内选中图片时，滚轮按比例调整显示大小；未选中图片时仍滚动正文。沿用原生撤销、重做、原图像素及空闲自动保存，连续滚轮不逐次写盘。
7. 回归发现带 WMF 图片的已保存便签在副屏首次显示时，RichEdit 可能把目标显示尺寸重置为图片固有尺寸。现在在首次布局完成后恢复保存的富文本快照，并在真实编辑时使快照失效；首次显示前已保存的修改使用最新快照。

## 证据与验证

- 旧 v1.4.13 包使用相同专项运行器时，在两块真实 144/120 DPI 屏幕间出现 320×220 图片控件变成 267×183 或 384×264；连续滚轮后实际画面和完整重绘结果有 336 个残留像素差异。13 项截图专项中 6 项失败。
- 修复版在相同屏幕上保持 320×220 的 1:1 视口，原图内侧像素与实际已绘制窗口逐像素一致。连续滚轮不让出绘制队列的测试中，残留像素为 0。
- 额外模拟 DPI 建议矩形和子控件缩放，验证画布尺寸不会漂移；这些模拟检查与真实跨屏检查分别执行。
- `tests/display.ps1`：23 项通过，包含默认宽度、链接分派、首次显示前的编辑/保存及文字样式保护。
- `tests/run.ps1`：388 项通过，包含截图、标注、保存、贴图历史、便签布局、缩放与撤销/重做、混合 DPI、待办、设置、快捷键和无痕模式。
- `tests/cloud.ps1`：73 项通过，确认初次显示的修复没有破坏桌面文档保存与云同步。
- Release 构建及 `git diff --check` 通过。测试数据使用独立临时目录，未改动用户便签目录。
